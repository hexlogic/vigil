# Decisions

One short paragraph per decision. Dependencies get a one-line reason (see CLAUDE.md).

## Toolchain pinned to an exact stable release

`rust-toolchain.toml` pins `1.99.1` (latest stable at project start, 2026-10) with the `minimal` profile plus `rustfmt` and `clippy`. `rust-version` in the workspace is `1.99`. CI reads the same file, so local and CI toolchains match.

## `unwrap`/`expect` enforced by lint, not just by convention

`clippy::unwrap_used` and `clippy::expect_used` are `warn` in `[workspace.lints]`; with `-D warnings` in CI they fail the build. `clippy.toml` allows them inside tests. Binary startup code that genuinely needs one uses a targeted `#[allow]` with a reason.

## `publish = false` until the name is cleared

The workspace sets `publish = false` so nothing can reach crates.io by accident. Remove it only after searching crates.io, GitHub and Docker Hub for name collisions (PLAN.md header).

## Storage conventions

IDs are UUID v7 stored as `TEXT` (sortable by creation time, no extra index tricks). Timestamps are `INTEGER` unix milliseconds. Nested watch configuration (`fetch`, `schedule`, `pipeline`, `conditions`) is stored as JSON `TEXT`: these structures evolve with the pipeline and are always read and written whole, so columns would only add migrations. Hashes (blake3) are `BLOB`. Snapshot content is a zstd `BLOB`.

## Runtime SQL queries, not `sqlx::query!`

Phase 0 uses runtime-checked queries so builds need no `DATABASE_URL` or offline query data. Revisit when the query surface grows (Phase 1+).

## Migrations run on open

`Store::open` runs the embedded migrations. When an existing database (one that has applied at least one migration) has pending ones, `VACUUM INTO <db>.backup-v<latest applied>-<unix ms>` writes a consistent copy first (a plain file copy of a WAL database can miss the `-wal` file). A fresh or up-to-date database is not backed up, a failed backup aborts the open, and old backups are never deleted. A backup holds everything the database holds, including notification target secrets.

## Configuration layering

`figment`: built-in defaults, then an optional TOML file (`--config` / `VIGIL_CONFIG`, default `./vigil.toml` if present), then `VIGIL_*` environment variables (nested keys use `__`). `VIGIL_CONFIG` is excluded from the config keys because it selects the file rather than configuring the app.

## Text processor (Phase 1)

HTML is rendered with `html2text` in plain mode at a width of 10,000 columns so text is never re-wrapped, and without link decoration, which means link targets are not part of the compared text yet. Non-HTML bodies pass through untouched. A response is treated as HTML when its `Content-Type` says so, or by sniffing a doctype or `<html` when the header is missing. All text is normalised (LF endings, trailing whitespace trimmed, blank runs collapsed) before hashing so cosmetic differences never register as changes.

## Charset decoding

The charset comes from the `Content-Type` header and defaults to UTF-8. A byte-order mark in the body wins over the header, malformed bytes decode to U+FFFD instead of failing the check, and charsets that encoding_rs maps to its REPLACEMENT encoding (iso-2022-kr, iso-2022-cn, hz-gb-2312) are treated as unknown, because REPLACEMENT turns every page into a single U+FFFD and would hide all changes. When the header gives no usable charset, the first 1024 bytes of an HTML or XML body (or of a body with no content type) are searched for a declaration: `<meta charset>`, `<meta http-equiv="content-type">`, and the `encoding` of a leading `<?xml?>` declaration. `<meta>` is only read in HTML, never in other XML, and nothing is read in JSON or plain text. As in browsers, a declared UTF-16 means UTF-8 (the page is readable as ASCII, so it cannot be UTF-16) and `x-user-defined` means windows-1252. Order: BOM, header, declaration, UTF-8. Accepted one-time effect: a page that declares a charset the header leaves out is decoded differently than before, so its hash changes once on the first check after upgrading.

## Snapshot storage and check recording

Both `record_success` and `record_error` run in a `BEGIN IMMEDIATE` transaction so a `vigil check` run next to `vigil serve` queues for the write lock instead of failing with `SQLITE_BUSY_SNAPSHOT`. A snapshot is stored only when the blake3 of the processed text differs from `watches.last_hash`. A 304 or an identical body only updates `last_checked_at`. The first successful check is logged as `changed` in `check_log` because its outcome column only allows `unchanged`, `changed` and `error`. Retention keeps at least one snapshot even if a watch says 0, and the check log is trimmed to the newest 500 rows per watch on every write.

## Watch ids on the command line

Ids are UUID v7, whose leading 48 bits are a millisecond timestamp, so watches created in the same sitting share long prefixes. The CLI therefore accepts a full id or a unique *suffix* of at least 6 characters, never a prefix.

## Runtime SQL queries (revisited)

Phase 1 adds about a dozen queries. They stay runtime-checked `sqlx::query(...)` calls and are covered by integration tests against a real SQLite file, which keeps builds free of `DATABASE_URL` and offline query data.

## Fetcher behaviour

TLS is rustls through reqwest's `rustls` feature, which uses the aws-lc-rs crypto provider and the platform certificate verifier; `cargo tree` shows no OpenSSL or native-tls. Revisit armv7 musl builds in Phase 6. Redirects stop after 10 hops, cookies are off, and proxies are off too: the client calls `no_proxy()` because reqwest otherwise reads `HTTP_PROXY`/`ALL_PROXY` from the environment, which would silently reroute every fetch (proxy support comes later, per watch and as a global setting), and only `http`/`https` URLs are accepted, so `file://` is never fetched. The size cap applies to the decompressed body, checked chunk by chunk, so a small gzip bomb cannot slip past a `Content-Length` check. `If-None-Match`/`If-Modified-Since` are sent only when the watch has stored validators, and a 304 is accepted only in that case; an unsolicited 304 is reported as an error. Bodies are returned as `Vec<u8>` rather than `bytes::Bytes` to avoid a direct dependency.

## Scheduler design

PLAN.md describes workers pulling from a bounded channel. The scheduler instead spawns one task per due check into a `JoinSet`. Each task first takes its host slot and then a global slot, so a check queued behind a busy host never holds a global slot, which a fixed worker pool would not avoid without head-of-line blocking. One task owns a min-heap of `(due, watch)`; heap items that no longer match their entry are skipped when popped. The scheduler talks to its watches and checks through the `Backend` trait, which lets tests drive it with a fake and a paused clock, and the real `Checker` implements it. The watch list is reloaded every 30 seconds, so adds, removals and pauses take effect without a signal. Delays are `interval * 2^errors` capped at 6 hours and never below the interval, plus random jitter, either the watch's `jitter_secs` or a tenth of the interval up to 60 seconds. Intervals are kept between one second and 365 days (`vigil watch add` rejects values outside that, and the scheduler clamps whatever is stored), all waits are saturating and bounded so a corrupt or absurd value cannot overflow time arithmetic, and a last-check time in the future (the clock was set back) delays a watch by at most one interval. On shutdown the scheduler stops starting checks (a check still waiting for a concurrency slot is dropped, not started) and waits up to 30 seconds for the ones already running.

## Check errors

A page that cannot be fetched or processed is not an error of the checker: it is recorded on the watch and in the check log, and `Checker::check` returns it as `CheckResult::Failed`. Only store failures, including a deleted watch, are returned as `Err`. Error messages include the source chain on one line, for example `request failed: error sending request for url (...): client error (Connect): ...`.

## Command-line behaviour

`vigil watch add` defaults to checking every hour (`--every 1h`) and rejects intervals under one second. `vigil watch remove` is not in PLAN.md but is the only way to undo a mistyped add before the UI exists. Commands accept a full watch id or the last six or more characters of it. `vigil check` exits non-zero when the page could not be checked, so it works in scripts; `vigil diff` with fewer than two snapshots prints "nothing to compare yet" and exits zero. Diffs are colored only when stdout is a terminal and `NO_COLOR` is unset. One-shot commands log at `warn` to stderr so stdout only carries their results; `serve` logs at `info` to stdout. CLI output is plain English in the binary and is not covered by the `locales/*.toml` rule, which is about web templates. `vigil serve` runs the scheduler next to the HTTP server and shares one cancellation token with the server's graceful shutdown.

## Unreadable watch rows

`list_watches` logs and skips a row it cannot interpret instead of failing, because the scheduler and `vigil watch list` both depend on it and a single bad row would otherwise stop all checking. `get_watch` still returns the error for that row.

## Scheduler failure stops the server

`vigil serve` watches the scheduler task. If it ends before a shutdown was requested (for example after a panic), `serve` exits with an error instead of carrying on answering `/healthz` while nothing is checked, so systemd or Docker can restart it.

## Request headers

Per-watch headers replace a default of the same name (`User-Agent`, `If-None-Match`, `If-Modified-Since`) instead of being sent beside it. A header that makes the request conditional also makes a 304 acceptable. The stored `ETag` and `Last-Modified` are sent only when the watch's method is GET (see "Request method and body"); a conditional header the user sets is theirs and still makes a 304 acceptable for any method. Errors about an unusable header name the header but never include its value, since values often hold tokens and these messages end up in the check log. Custom headers are still forwarded if a page redirects to another host; restricting that is future work.

## Request method and body

A watch's `fetch` settings gain `method` (`GET`, `POST`, `PUT`, `PATCH` or `DELETE`, in capitals in JSON) and `body`. Both are left out of the stored JSON while they are the default, so existing rows and `watch show` output keep their shape. `HEAD` and `OPTIONS` are not offered: they carry no page to compare. A body needs a method that carries one, and is at most 1 MiB; `FetchSettings::validate` checks both and the form, the CLI and the API all call it. The body is sent exactly as typed and no `Content-Type` is added, because the right one depends on the server (`reqwest` adds none for a text body); the user sets it in the headers, and importers add it explicitly. A form posts line breaks as CRLF, which the form turns back into LF so a body the user wrote is the body that is sent. The stored validators (`If-None-Match`, `If-Modified-Since`) are sent only for GET: the response to a POST is not a page that can be "not modified", and a server that answered 304 to one would never send the body again. `vigil-fetch` stays independent of `vigil-core` and re-exports `reqwest::Method`; the scheduler maps one to the other.

## Patterns

A pattern is a plain substring, matched case-insensitively with Unicode simple case folding (so Cyrillic works), or `/regex/flags`. The regex form needs a non-empty body between two slashes and only the flags `i m s x U` after the last slash; anything else is plain text. That makes `//`, `/` and `/foo/g` plain, and `/api/v1/` the regex `api/v1`, which also matches a path with that text in it. Wrap a path in a character class or add a flag (`/\/api\/v1\//i`) to be exact. Empty patterns are rejected because they would match every line. All regexes, including the raw ones in the regex steps, are built with a 1 MiB size limit, and error messages keep only the one-line reason so they fit the check log.

## JSON processor

The `json` processor parses the body (any content type) and prints it with two-space indentation, object keys sorted at every level, arrays in their original order and one trailing newline, so key order and formatting never register as changes. Keys are sorted by our own printer rather than by the map type, because `serde_json` keeps insertion order as soon as any crate in the build enables `preserve_order`. Numbers go through `serde_json`: integers that fit 64 bits stay exact, larger ones become floating point and lose precision, and `1.0` stays `1.0`. Nesting is limited to 128 levels (the parser's own limit, applied to values built by later steps too) and any step's output to 16 MiB, so a small input cannot make a check use unbounded memory. A body that is not JSON fails the check with the parser's message.

## Feed processor

Each entry becomes up to three lines (title, link, date) and entries are separated by a blank line. The date is `published`, or `updated` when there is none, converted to UTC and printed as `2026-10-12T09:00:00Z`. Entries are sorted newest first; entries without a date come after the dated ones in the order the feed lists them (the sort is stable). Lines the feed leaves out are left out, and an entry with no title, link or date is skipped. Entry ids and summaries are not part of the text: feed software generates ids when a feed has none, and summaries are often rewritten without the item changing. Feed-level data (channel title, build date) is not part of the text either, so a feed that touches `lastBuildDate` on every request does not look changed. The link is the `alternate` one when an entry has several. Titles collapse inner whitespace so line wrapping in the source does not matter. The body has already been decoded by `decode`, so every `encoding` in the feed's XML declarations is rewritten to UTF-8 before parsing; otherwise the parser would decode the text a second time and garble it. All declarations are rewritten, not only the first, because fuzzing found that a second one naming another encoding makes `quick-xml` panic; a panic that still gets through is caught and reported as an unreadable feed.

## Pipeline and text steps

`Pipeline::render(bytes, content_type)` is the single path from a fetched body to the stored text: decode, processor, `normalize`, then each step, normalising after every step so each one sees tidy lines and the result always ends in exactly one newline. Checks and previews both call it, so a preview cannot differ from what a check would store. Steps are stored as plain JSON (`{"type": "regex_extract", ...}`, internally tagged, unknown fields rejected, variants only ever added) and compiled by `Pipeline::new`; a bad regex, pattern or capture group is reported there with the step's number and name, so the CLI can refuse it when a watch is saved and a check reports it without fetching anything useless. Text steps work on lines. `regex_extract` keeps each match (or one capture group) on its own line, skips empty matches, and leaves empty text when nothing matches (see "Empty selections"); `regex_replace` with no match is a no-op, and a replacement that names a capture group the pattern does not have is refused when the step is built: the `regex` crate reads `$1USD` as the group called `1USD`, which does not exist, and silently replaces it with nothing, so the text after the group would vanish (`${1}USD` is what was meant, and the error says so). `sort` is byte order, `unique` keeps the first occurrence anywhere in the text, `trim` strips both ends of each line, `collapse_whitespace` turns every run of whitespace into one space (so an indented line keeps one leading space), and `lowercase` is full Unicode lowercasing. The raw `regex_*` steps take plain regex syntax with `(?i)`-style inline flags; only `ignore_lines`, triggers and block text use the shared pattern syntax. A step's output is capped at 16 MiB, checked while it is produced.

## CSS step

`css` runs before the page becomes text, so it is only valid with the `text` processor and must come before every other kind of step; both rules are checked when the pipeline is built. The page is parsed as HTML whatever its `Content-Type` says, since asking for a selector is asking for HTML. `include` keeps only the selected elements, in document order; an element inside another selected element is skipped because its text is already part of the outer one. Each kept element goes in its own block, so inline matches such as prices end up on separate lines. Table rows and sections are put back into a table so the HTML parser does not throw their tags away, which means html2text draws them with borders; table cells are reduced to their content so `td.price` gives just the price. `include` that selects nothing leaves an empty page. `remove` detaches the selected elements and does nothing when there are none; later steps select by walking the tree from its root, because the library's own `select` walks every node ever allocated and would match elements inside the detached subtrees, bringing removed content back; removing `html` or `body` leaves an empty page. The kept or edited page is serialised once and converted with the same html2text settings as the plain `text` processor.

## XPath step

PLAN.md left the XPath crate open, so three designs were compared on what the step needs: pure Rust, tolerance for broken HTML, both `include` and `remove`, no extra HTML parser, and survival under fuzzing. `skyscraper` has its own tree and parser and its author warns the API will break before 1.0; selecting with it would mean a second HTML tree that cannot be edited or serialised for html2text. `sxd_html` (html5ever into `sxd-document`) was last released in August 2024, would add a third html5ever, and `remove` would need an XML-only serialiser whose self-closing tags change how HTML is parsed. The choice is `sxd-xpath` over a copy: the page stays a `scraper` tree, each `xpath` step builds a read-only `sxd-document` copy of its elements and text, evaluates the expression there, and maps the returned nodes back to the page's node ids (the node types hash by identity). CSS and XPath steps therefore edit one tree and share the same include and remove code, and html5ever parses everything. Costs: `sxd-xpath` has seen no release since 2020 and only speaks XPath 1.0, and the copy is rebuilt per XPath step. Expressions are evaluated without namespaces, so `xlink:href`-style names do not match. The copy refuses pages nested deeper than 256 elements because the evaluator recurses; real pages are far shallower. An expression that is slow on a large page is not interrupted here; the scheduler's per-check timeout bounds it.

`include` takes elements and text nodes as written, plus attribute values (`//a/@href`) and computed values (`count(//li)`, `string(//h1)`), which become text; a result that is empty text counts as nothing, like an empty selection. `remove` can delete elements and text nodes only and rejects expressions that yield attribute values or computed values. `/` selects the document element. Computed values are written as XPath writes them (`Infinity`, `-Infinity`, `NaN`, `true`, and a single `0`), not as Rust prints floats. Error messages from the library, which are bare variant names such as `EmptyPredicate`, are turned into words.

## JSON steps

JSON steps (`jsonpath`, and later `jq`) work on the parsed value of the `json` processor, come after any HTML steps and before text steps, and are rejected with other processors when the pipeline is built. A JSONPath step always produces an array of its matches, even for a single match, so the shape of the stored text does not flip between an object and a list as results come and go; finding nothing gives `[]`, like jq. The array is printed by the same canonical printer as the `json` processor. Matches can overlap (`$..*` returns every value inside every other one), so their approximate total size is checked against the 16 MiB output cap before anything is copied.

## jq step

A `jq` step runs a jaq program on the `json` processor's value and collects its outputs into an array, so one output and many outputs have the same shape; no output gives `[]`, because a jq program says what is empty (`select`, `empty`) and appending `| if length == 0 then error("nothing") else . end` makes it an error. Programs are user input, so the engine is fenced in. Programs over 2 KiB or nested deeper than 32 brackets are refused before parsing, since the parser recurses and a stack overflow cannot be caught (see "Input limits"). Filters that read the machine, the clock or other streams are removed, so a program gives the same answer for the same input everywhere: `env` (and so `$ENV`), `now`, `input`, `inputs`, `debug`, `stderr`, `input_filename`, `localtime` and `strflocaltime`. `halt` and `halt_error` are removed as well, and the library's `unwrap_valr` is not used, because it calls `std::process::exit` on `halt`. The definitions in the standard library that are built on the removed filters are dropped with them; a definition that uses a missing filter would fail to compile and take every program with it. Date functions that do not depend on the clock or the local time zone (`todate`, `fromdateiso8601`, `strftime`, `mktime`, ...) stay. At most 10,000 outputs and 16 MiB are accepted. Values cross between `serde_json` and jaq directly (jaq's own `serde` support in, a small converter out) rather than through text. Going out, what JSON cannot hold is mapped as jq prints it: NaN becomes `null`, infinity the largest finite number, and a byte string text with invalid bytes replaced; an object key that is not text is an error. jaq shares sub-values, so a few nodes can describe an enormous tree; the converter charges its size budget as it copies, so such a value stops at 16 MiB instead of exhausting memory. Compilation errors are reported when the pipeline is built, with the byte offset of a syntax error or the name and arity of an undefined filter; the program is compiled again for every run, because the compiled form borrows from its arena and the compile cost is small next to a fetch. Known gaps: a program that never produces output (`repeat(.)`, `def f: f; f`) is not interrupted by the engine, and one that recurses without bound may exhaust memory or the stack; the scheduler's per-check timeout covers the first, and `vigil preview` is the way to try a program before saving it.

## Empty selections

A selection step (`css`, `xpath`, `jsonpath`, `regex_extract`) that finds nothing gives an empty result: an empty page, `[]`, or empty text. The check succeeds and the empty text is stored like any other. This was first built as a failed check so that a site redesign would show up as an error instead of looking like every line was deleted, but failed checks back off (the wait doubles per consecutive failure, up to 6 hours) and a watch on something that is empty most of the time (new listings, a sold-out badge, items on sale) would fail, slow down, and then store its first real content as a baseline, so the moment the item appeared would go unreported. Each selection step takes `"required": true` to get the stricter behaviour back: when it finds nothing the check fails with `step N (type): matched nothing`. It applies to `remove` mode too. Without it, a redesign that empties the selection shows up as a change to empty text, which the trigger and block conditions can see. For `xpath`, an empty computed string (`string(//missing)`) counts as nothing; for `css`, a selector that matches an element with no text still counts as a match. The flag is omitted from the stored JSON when false, so existing configs keep their shape. `jq` has no flag: its program decides what is empty.

## Conditions

`conditions` only decide whether a change is announced, never whether it is stored: every change becomes a snapshot and a `check_log` row (`changed`) whatever the verdict, so history is complete and loosening a condition later does not lose anything. They produce a `Verdict { notify, reason, triggered_text }` from the line diff, and the scheduler hands it to the notification step. The shape of a change is `added` (lines were only added), `removed` (only removed) or `changed` (both), and `notify_on` switches each off; all three default to on, and `{}` notifies about everything. Evaluation order: a switched-off shape does not notify; an added line matching any `block_text` pattern does not notify; with `trigger_text` set, at least one added line must match one of its patterns, and the matching lines become `triggered_text`. By default patterns only look at added lines, so a change that only removes lines never satisfies a trigger. `scope` (`added`, the default, or `text`) widens that to every line of the new text, changed or not: with `text`, a `block_text` pattern blocks while any line of the new text matches it and `trigger_text` needs a match anywhere in it, which is how pages that say "out of stock" on an unchanged line are usually watched. `text` does not see removed lines; looking at those would be another value with its own name. The scope is left out of the stored JSON when it is `added`, and a change blocked or held back by a `text` scope says so in its reason (`no line of the text matches trigger_text`). Patterns use the shared syntax (substring or `/regex/flags`) and are compiled when the watch is saved, with the list name and position in the error (`trigger_text[1]: ...`). Unknown fields are rejected so a misspelt option cannot silently do nothing.

## Editing a watch

`Store::update_watch` replaces a watch's settings and keeps its pause flag, hash, snapshots and log. It also clears the failure streak and last error, so an edit that fixes a failing watch does not wait out its backoff. It clears the remembered `ETag` and `Last-Modified`: a server that answers 304 to the conditional request would never send the body again, and an edited pipeline would never run. A check that was already running when the edit happened would write its own validators back, from a response processed with the old settings; every check therefore carries the `updated_at` of the watch it was made with (`CheckSuccess::settings_version`, which `update_watch` always increases), and `record_success` drops the validators of a result whose version no longer matches. The cost is that the first check after an edit compares the new output with the old snapshot and may report a change; re-baselining on edit is deliberately not built, and `vigil preview` is how to see the new output before saving. `pipeline` and `conditions` are stored as JSON in the existing columns, with no migration. A row whose JSON does not parse (a step type from a newer version, say) is skipped by `list_watches`, as unreadable rows already are, and `get_watch` reports the error. A step that parses but does not compile (a bad regex or selector) does not hide the watch: the watch is still scheduled and each check fails with the step's number and name. A watch's notification template is kept in the existing `notification_template_override` column and is written by `set_notification_template`, not by `update_watch`: it changes neither what a check fetches nor when it runs, so it leaves `updated_at`, the validators and the failure streak alone.

## Processing runs on its own thread

A check builds the watch's pipeline and renders the response on a dedicated `std::thread` and waits for it with a 30 second timeout (`Checker::with_render_timeout` changes it for tests). Processing is CPU work on untrusted input, so it stays off the async workers, and it does not use `spawn_blocking`: the runtime waits for blocking tasks when it shuts down, so a jq program that never ends would hang `vigil serve`. When the timeout passes, or the thread panics, the check fails with `processing timed out after 30s` or `processing panicked` and releases its host and global slots; the runtime does not wait for a detached thread. The cost is that a runaway thread keeps its CPU until the process exits, since nothing can interrupt it. So that retries do not add a runaway thread each, a watch whose earlier processing thread is still alive is refused a new one (`an earlier processing of this watch is still running`), which bounds a stuck watch at one thread; a cap of 32 live threads bounds many stuck watches, and the slot is released before the result is sent so a finished thread never refuses its own watch's next request. The thread has a 16 MiB stack (address space, not memory in use) because parsing and printing nested documents recurse. The pipeline is built on that thread, so nothing in it has to be `Send`. Conditions are compiled and the pipeline is built (on that thread) before the fetch, so a watch with an invalid pattern, selector, regex or program fails without making a request; a watch with a stuck thread does not fetch either. The conditions' verdict is carried on `CheckResult::Changed`; the check log still says `changed`, since the change was stored.

## Preview

`Checker::preview(&Watch)` fetches the page and renders it exactly as a check would (same `Pipeline::render`, same thread and timeout), then compares the text with the watch's newest snapshot and runs the conditions on that difference, without recording anything: no snapshot, no `check_log` row, no change to the watch's state or error count. It takes a `&Watch` rather than an id so that unsaved edits and command-line overrides can be previewed; only the id is used, to find the snapshot. The request carries no `If-None-Match` or `If-Modified-Since`, since a 304 has no body to show. A watch whose own headers make the request conditional can still get a 304, which is reported as a preview error. Problems with the page or the configuration come back in the report and never count against the watch. Previews fetch a fresh response every time; raw responses are not stored (PLAN.md allows "last raw response"), which keeps the database free of up to 10 MB per watch. The Phase 4 editor can hold the body it fetched while the user edits.

## Configuring watches from the command line

`watch add` and `watch edit` take `--processor`, `--pipeline` and `--conditions`; `--pipeline` and `--conditions` take JSON inline or `@path` to a file holding it, in the same shape that is stored, so what `watch show` prints can be pasted back. Each option replaces that part of the watch as a whole; there is no way to add one step, because the order of steps matters and a list edited in place is easy to get wrong. The merged result is validated before anything is saved (steps against the processor, selectors, regexes, patterns), so a typo is refused with the step's number and nothing is written. Changing only `--processor` on a watch whose steps do not fit it is refused with a hint to replace the steps too. `watch edit` with no option is an error rather than a silent no-op. `watch show` prints the settings as JSON (not the check state), which the REST API in Phase 5 will mirror.

## `vigil preview`

`vigil preview <id>` prints, in order: a status line (HTTP status, content type, size, time), the processed text, a unified diff against the newest snapshot (coloured on a terminal unless `NO_COLOR` is set) or a note that there is none or no difference, and whether the conditions would notify and why. `--processor`, `--pipeline` and `--conditions` override the saved settings for that run only, with the same validation as `watch add`, so a pipeline can be tried before `watch edit` saves it. It exits non-zero when the page or the settings do not work, so it can gate a script. `vigil check` now also says when a stored change would not notify (`no notification: no added line matches trigger_text`), since the change is stored either way and the output would otherwise read as if it were announced.

## Deeply nested pages

Parsing and rendering HTML take more than linear time in the nesting depth: the parser searches its stack of open elements for most tags, and html2text does more on top. Measured in a debug build, 40,000 nested `<div>`s took 37 seconds and 80,000 took over 100; a megabyte of nesting would keep a core busy for minutes, and the check's timeout can only abandon the thread, not stop it. A page nested more than 512 elements deep (not counting elements the parser closes by itself, such as unclosed `<li>` and `<p>`) therefore fails the check with `the page nests elements deeper than 512 levels` before it is parsed. The guard cannot use the parsed tree, since parsing is the slow part: it reads the markup in linear time the way the tokenizer does (comments, declarations, raw-text elements such as `<script>`, quoted attribute values), keeps a stack of open element names, ignores end tags that match nothing open as the parser does, and stops as soon as the stack passes the limit. Inside `<svg>` and `<math>` it follows the foreign-content rules, where a trailing `/>` closes the element (so thousands of `<path/>` siblings are not nesting), unless the tag is an HTML element that breaks out of foreign content or sits inside a place where HTML is parsed again (`foreignObject`, `title`, ...); outside them `<div/>` stays open, as in HTML. It follows every way the tokenizer ends a comment (`-->`, `--!>`, `<!-->`, `<!--->`). It applies to the plain `text` processor and to pipelines with HTML steps. Real pages are far shallower (rarely past 100); the XPath step's copy has its own, lower limit of 256 because the evaluator recurses. The guard is lexical, so a page crafted to fool it (an attribute value the tokenizer reads differently, say) falls back to the thread timeout.

## Fuzzing

`crates/vigil-core/fuzz` holds a `cargo fuzz` target, `pipeline_html`, that runs arbitrary bytes through ten fixed pipelines (the empty one, CSS and XPath include and remove, a long chain of text steps, JSONPath on the `json` processor, and the `feed` processor) with the content types that make sense for each. Errors are expected; panics, hangs and stack overflows are the findings. jq programs are not generated, because a valid program can run forever and the fuzzer could only call that a timeout. The crate is its own workspace so that it does not inherit `unsafe_code = "forbid"` (the fuzz macro generates `#[no_mangle]` items) and so that stable builds never see it; it needs a nightly toolchain and `cargo install cargo-fuzz`. Run it from `crates/vigil-core`: `mkdir -p fuzz/corpus/pipeline_html && cargo +nightly fuzz run pipeline_html fuzz/corpus/pipeline_html tests/fixtures -- -max_total_time=60 -max_len=16384 -rss_limit_mb=2048`. The first directory receives new inputs and is ignored by git; the fixtures are seeds only. `libfuzzer-sys` turns every panic into a crash, including ones the pipeline would catch in production, so a caught panic still counts as a finding. The first runs found a panic inside `quick-xml` (a second XML declaration in a feed) and the super-linear cost of deeply nested HTML; both are fixed and recorded above.

## Input limits

The CSS selector parser, the XPath parser and evaluator, and the jq parser recurse, and a stack overflow aborts the whole process, so it cannot be caught the way a panic can. A release build overflowed a 2 MiB stack at about 1,000 chained jq operators (`-----...`, `.|.|.|...`) or about 500 nested `:not(`; the command line checks steps on the 8 MiB main thread and checks run on a 16 MiB thread. Bracket nesting alone is not enough, since chains of operators recurse too, so every selector, expression and program is also limited in length: 1 KiB for CSS and XPath, 2 KiB for jq, and brackets nested at most 32 deep in all three. Real ones are a few dozen bytes. Errors quote only the start of an oversized input. This bounds parsing; it does not bound what a jq program does when it runs. A program that recurses without limit (`def f: 1 + f; f`) or builds a very deeply nested value overflows the stack at run time and aborts the process, and the compile-time limits cannot see it. Running jq in a child process that can be killed is the fix and is left as a follow-up.

## Rescheduling after an edit

The scheduler reloads the watch list every 30 seconds. A watch it already knows keeps its place in the schedule, unless what the store says about its timing has changed since the last reload: its interval, its jitter or its failure streak. Then its next check is recomputed from its last check time, as if it had just been seen, and the old queue entry is skipped. Otherwise `vigil watch edit --every 5m` on a daily watch would wait out the day, and an edit that fixes a failing watch (which resets the streak) would wait out the backoff, up to 6 hours. The comparison is with what was last loaded, not with the scheduler's own copy, so a check whose result could not be recorded (which the scheduler counts as a failure locally) is not mistaken for an edit. An edit that changes neither leaves the schedule alone: its pipeline applies to the next check at the usual time.

## Delivery log

Notification results go in a new `delivery_log` table (migration 0002), not in `check_log` as PLAN.md section 7 words it. A check can notify several targets, delivery happens after the check's transaction has committed and retries can take minutes, `check_log` is trimmed to 500 rows and its `outcome` CHECK constraint cannot be changed without rebuilding the table, and a test notification has no check at all. Rows are trimmed to 500 per watch (per target for test notifications, which have no watch). `snapshot_id` has no foreign key because snapshot retention prunes snapshots.

## Notification targets

Target names are unique (a unique index in migration 0002; nothing wrote the table before, so existing databases cannot violate it). Commands resolve a target by exact name first, then by full id or a suffix of at least 6 hex characters, as for watches. Disabled targets stay linked but are skipped when notifying. The URL is stored as typed, in plaintext, like the rest of the database: it holds credentials, so it is never logged or printed unredacted.

## Notification URLs

A target is a URL: `ntfy://`, `ntfys://`, `tgram://`, `discord://`, `slack://`, `mailto://`, `mailtos://`, `json://`, `jsons://`, `form://`, `forms://`, `gotify://`, `gotifys://` (`forms://` and `gotifys://` are the HTTPS twins of `form://` and `gotify://`, added for symmetry). Schemes without an `s` use plain HTTP, as people expect from URLs of this kind; the CLI warns when one sends a credential to a host other than this machine. `tgram://`, `discord://` and `slack://` are split by hand because a Telegram bot token (`123456:ABC`) would read as a host and a port to a URL parser. Option values are percent-decoded and nothing else (a `+` is a plus, not a space, so `to=me+vigil@gmail.com` and tokens survive). Options are strict: an unknown or repeated option is an error, and the error never names it (a mistyped URL can put a credential where an option name goes). No error quotes the URL. The ntfy topic is a secret (on a public server it is the only protection), so it is redacted like a token. Webhook URLs (`json://`, `form://`) keep their query string verbatim, since it is where webhook tokens usually go; they are held as a `SecretUrl` so a derived `Debug` cannot print them.

`mailto://` requires an upgrade with STARTTLS (default port 587). `?tls=none` sends plaintext (default port 25), meant for a relay on the same machine or network, and is refused with a password unless the host is `localhost` or a loopback address. `mailtos://` uses TLS from the first byte (default port 465) and rejects `tls=`. The sender is `from=`, or the user name when that is an email address; recipients are `to=` (comma separated or repeated), defaulting to the sender.

## Notification templates

Templates are `minijinja`. Variables: `watch_id`, `watch_name`, `watch_url`, `diff_added` and `diff_removed` (lines joined by newlines), `diff_full` (unified diff, 3 lines of context), `current_snapshot`, `triggered_text` (a list), `checked_at` (RFC 3339, UTC), `vigil_base_url`, `diff_url` (both empty when `base_url` is not set), `truncated`, and `is_test` (true for a test notification, whose built-in messages leave out "changed"). A template may set the message title with `{% set title = "..." %}`; the title is used by channels that have one (email subject, ntfy, Gotify, webhooks) and defaults to `<watch name> changed`. A watch's template wins over the target's `default_template`, which wins over the built-in one for the channel. Templates are checked when saved by rendering a sample event for every kind of channel; undefined variables and unknown filters are errors (strict mode), and a render is stopped after 100,000 units of work. A template that fails when a message is sent (it can: the values differ from the sample) is replaced by the built-in one and the delivery log says so, because a notification is worth more than a pretty one.

Values printed by a template are escaped for the channel; the template's own text is not. This is done with `minijinja`'s auto-escape (a custom mode named after the channel, plus a custom formatter) rather than by escaping the variables in advance, which would break `length`, `join` and truncation. `|code` and `|link` return markup that is not escaped again. The built-in `|safe` filter is removed: it would let a template print page text unescaped, which is the thing the escaping prevents. Telegram uses `parse_mode: "HTML"` instead of Markdown (a deviation from PLAN.md section 7): MarkdownV2 needs `. - ! ( )` escaped, which would make users escape their own template text, while HTML needs only `& < > "`. Discord output is Markdown-escaped (a backslash before punctuation is an escape there) and is sent with `allowed_mentions` empty; Slack needs only `& < >` escaped, which also defuses `<!channel>` and `<@user>`.

Messages are cut to each service's limit (Telegram 4096 characters, Discord 2000 characters, ntfy 4096 bytes; Slack 4000 characters and Gotify 32,000 are conservative choices; email and webhook bodies 256 KiB). The long values (diff, added and removed lines, snapshot, triggered text) that the template actually prints are shortened on character boundaries, preferably at a line, sharing the room fairly, before escaping so that an entity or a tag is never split; "… truncated." and a link to the diff page are added at the end. Escaping can make the text longer than the raw values, so the budget is scaled down and the render repeated (up to four times) until it fits, then a minimal message is sent.

## Notification delivery

Messages are sent by a `Sender` with its own HTTP client: no redirects (a redirect could carry a token to another host), no proxy (like the page fetcher), a 15 second timeout per attempt, and a `vigil/<version>` user agent. A failed delivery is retried three times, after 2, 10 and 30 seconds (four attempts in all). Connection errors, timeouts, 5xx, 408 and 429 are retried, and a `Retry-After` of up to 60 seconds is honoured; any other status (a bad token, a missing topic) fails at once, since waiting will not fix it. So does a TLS setup problem: a certificate that is not valid (unknown issuer, expired, wrong name) or `https` against a port that speaks plain HTTP. These are recognised by rustls's wording in the error chain, because the types are not reachable through `reqwest`; a connection that is refused, dropped or times out is still retried. Cancelling the delivery's token stops the wait between attempts.

Errors are written to be shown. The request URL is dropped from network errors (`reqwest::Error::without_url`), and the reply of a service, cut to 200 characters, has the request path, query and every credential replaced by `***`, because some servers echo the path in their error page. Telegram, Discord and Slack are reached at fixed addresses held in `Endpoints`, which a library user (and the tests) can change; it also lets Telegram be pointed at a self-hosted Bot API server. There is no configuration key for it yet.

JSON bodies are built with `serde_json`, never by filling in text. Generic webhooks (`json://`, `form://`) receive the title, the message, the watch (id, name, URL), `checked_at`, `diff_url`, the added and removed lines and the triggered text (capped at 256 KiB each), and `truncated`; form webhooks get the same fields with the lists joined by newlines.

## Email

Email goes through `lettre`'s async SMTP client, one connection per message, as plain text with the title as the subject (non-ASCII subjects and bodies are encoded by `lettre`). The TLS rules are in "Notification URLs". The error is permanent (not retried) for a 5xx reply, a server that does not offer STARTTLS where it is required, and TLS failures; network errors, timeouts and 4xx replies are retried like any other channel. The password is removed from error text, and the timeout bounds the whole attempt (lettre's own applies to each step of the conversation). Authentication is sent only after the TLS policy is satisfied: `tls=none` with a password is refused at parse time unless the host is local, because `lettre` itself would send `AUTH` over a plaintext connection.

The tests run `lettre` against a small SMTP responder in `crates/vigil-notify/tests/support/smtp.rs` (plaintext, no STARTTLS) instead of a stub transport, so the real message building and the real client are exercised, and it needs no dependency. Only the plaintext and refusal paths can be tested that way: STARTTLS and implicit TLS success are covered by `lettre`'s own tests, and here only by checking that they fail safely against a server that does not speak TLS.

## Test notifications

PLAN.md Phase 3 asks for a test endpoint, but there is no API or login yet (auth arrives with the web UI, the API in Phase 5), and an unauthenticated endpoint that makes the server send to arbitrary configured targets is not something to ship. A test notification is `vigil notify test <target>` on the command line, backed by `send_test()` in `vigil-notify`; the HTTP endpoint and the UI button follow once there is auth. A test notification is titled "Vigil test notification" and says it is a test, tries the target's own template (so a broken template shows up there, not on the first real change), links to Vigil when `base_url` is set, and is retried like any other delivery by the library. Its result is recorded in the delivery log with no watch.

## Notification dispatch

A check that finds a change the watch's conditions want a notification for (`Verdict::notify`) hands it to the `Notifier` (attached with `Checker::with_notifier`, so existing callers and tests are unchanged), which loads the watch's linked, enabled targets and delivers to each on a background task (`TaskTracker`). `check` returns as soon as the tasks are spawned, so the scheduler's host and global slots, which are held only while a check runs, are released before any request to a notification service, and retries (up to a minute) never delay the next check of the watched site. Delivery cannot change a check: it never turns it into `CheckResult::Failed`, never adds to `consecutive_errors` and never causes a backoff, because the page was fetched fine. Each delivery writes one row to the delivery log (`sent`, or `failed` with the attempts and the reason; a template that fell back to the built-in one is noted there too). A baseline never notifies.

The watch's template wins over the target's `default_template`, which wins over the built-in one. The diff page link is `<base_url>/watch/<watch id>/diff?from=<previous snapshot>&to=<new snapshot>`, a path the web UI will serve; with no `base_url` the link is left out. `diff_full` is a unified diff with 3 lines of context.

`vigil check` waits for its deliveries (`close_and_wait`, no time limit: the user is looking at the terminal). `vigil serve` gives them 30 seconds after the scheduler has stopped (`shutdown`): waiting to retry stops at once and attempts already on the wire get the grace period; a delivery that was still waiting stays in the outbox (see "Notification outbox"). A target whose stored URL no longer parses (the parser was made stricter, or the row was edited by hand) is logged as failed with 0 attempts and a message that does not repeat the URL.

## Notification commands and `base_url`

`vigil notify add|list|remove|test` manage targets from the command line, as the web UI and API do not exist yet. `add` parses the URL and checks the template before storing anything, prints the redacted form, and warns on stderr when a secret would travel over plain HTTP to another machine (`Channel::sends_secrets_in_cleartext`: a password or token, an ntfy topic, or the path or query of a webhook); `list` never prints a stored URL unredacted. The URL is an argument, so it is visible in the shell history and the process list while the command runs; that is accepted for a single-user tool, and a prompt or file input can be added if it matters. `notify test` does not retry (someone is waiting at the terminal) and exits 1 when the notification failed.

`base_url` is an optional top-level setting (`VIGIL_BASE_URL`), checked at load to be an `http` or `https` URL; an empty value means unset. It is the one place Vigil is told its own address, which it cannot know behind a reverse proxy.

## Linking watches to targets

`vigil watch add|edit --notify <target>` links a watch to a target, `edit --no-notify <target>` unlinks it, and `--notify-template` sets the watch's template (an empty value removes it). Everything that can be refused (an unknown target, a template that does not validate, a settings error) is checked before anything is written, so a refused command changes nothing. Linking and the template call `link_target`, `unlink_target` and `set_notification_template` rather than `update_watch`: they do not touch `updated_at`, so the scheduler does not treat them as an edit, and they leave the validators and the failure streak alone. `vigil check` notifies by default (PLAN.md section 6 treats "check now" as a normal check), waits for the deliveries including their retries, prints `notified <target>` or the failure on stderr, and exits with the check's own status: a failed delivery is not a failed check. `--no-notify` skips it. `vigil serve` builds one `Notifier` and, after the scheduler has drained, gives deliveries 30 seconds.

## Notification outbox

A change is already the new baseline when its notification is built, so a notification that was lost (the process stopped while a delivery waited to retry, or died mid-delivery) would never be announced again: the next check finds the page unchanged. So each notification is saved in `notification_outbox` (migrations 0003 and 0004) before delivery and removed when delivery is over: sent, refused for good, or given up on after a day (those stay in the delivery log; see "Later tries" for what happens in between). A delivery stopped by shutdown reports `interrupted` and is neither recorded nor removed. `vigil serve` calls `Notifier::resume` at start-up, before the first check, and sends what is left. It does not run in `vigil check`, which might otherwise race a running server for the same rows.

The row holds the event the message is built from (JSON, zstd), without the page text, which is read back from the snapshot. The watch's template and the target are looked up again at resume time, so an edit in between applies; a target that was removed or disabled drops the row; a row older than a day is recorded as failed ("too old") instead of sent, because an alert that late is noise; a row that cannot be read is dropped. Retries start again from the first attempt after a restart.

## Later tries

The quick retries (2, 10 and 30 seconds) ride out a blip, not an outage. When they run out on a failure that may pass (`DeliveryReport::retryable`: a network problem, a timeout, a server error, 408 or 429; never a refusal or a TLS setup problem), the notification stays in the outbox with `next_attempt_at` and `rounds` set, and is tried again after 5 minutes, then 15, 30, 60 and 120 minutes, then every 4 hours, until it is sent, refused for good, or a day old. Each later round is a single attempt, since the wait is the retry. A try that would fall past the day is not scheduled: that failure is final. Every round is written to the delivery log (a failed row that says when it will try again, then the last row sent or failed), so the log shows what happened.

`next_attempt_at` NULL means a delivery is in progress (or was when the process died), and `vigil serve` resumes those once at start. A row with a time is picked up by a sweeper in `vigil serve` every 30 seconds; `Notifier::retry_due` claims each due row with a conditional UPDATE so that only one caller sends it. `vigil check` never sweeps: it tells the user that a failed delivery is kept and that a running `vigil serve` will send it. A waiting row survives restarts, and one saved by `vigil check` is sent by a server that is started later. Two processes that both sweep would not duplicate a delivery, but only the server is meant to.

## Diff view

`DiffView::between(old, new, context)` in `vigil-core` shapes a diff for the web UI: hunks of blocks, each line numbered on both sides, with the words that changed picked out. Unchanged runs are `Block::Same`; a replaced run is `Block::Changed { removed, added }`, and `Block::rows()` pairs the i-th removed line with the i-th added one for the side-by-side layout, while the inline layout lists all removed lines and then all added ones, as a unified diff does. Words are compared only for replaced runs (a pure insertion or removal is a whole line anyway) and only when the run is under 32 KiB; all the word comparisons of one view share a 300 ms budget. After that, lines are shown whole, so a large diff costs bounded time. A line that changed all through is not emphasized: its row colour already says so. A view holds at most 5000 lines and each line at most 2000 characters, and says `truncated` when it cut something, so a diff of two unrelated pages cannot become a page of tens of megabytes; the counts of added and removed lines still cover the whole diff. The text is returned unescaped; the template escapes it.

## Scheduler handle

`Scheduler::handle()` returns a cloneable `SchedulerHandle` that talks to the running loop over a bounded queue. `reload()` makes it load the watch list now, so a watch the web UI just added, edited, paused or deleted takes effect at once and not at the next 30 second resync (which stays as the safety net, and for edits made by the CLI in another process). `check_now(id)` returns a `Ticket` whose `wait()` resolves when that check has ended; the result itself is in the store. A requested check runs through the same global and per-host limits as a scheduled one. A watch that is already being checked, scheduled or requested, is not checked a second time: the new ticket waits for the running check. That matters beyond tidiness, since a second concurrent processing of one watch is refused and recorded as a failed check (see "Processing runs on its own thread"). A scheduled watch is next due one interval after the requested check ends, as after any check. A watch that is not on the schedule (paused) is looked up with `Backend::find`, checked once and left unscheduled; if it is resumed while that check runs, the schedule takes over when the check ends. A watch that does not exist ends as `RunOutcome::Gone`. A scheduler runs once: when it stops, queued requests are dropped and later ones fail with `Stopped`, so a handler never waits on a loop that is gone. The schedule bookkeeping moved to `state.rs` and the running checks to `runs.rs` to keep `scheduler.rs` under 400 lines.

## Previewing from the editor

The web editor previews on every pause in typing, so fetching on each preview would hit the site hard. `Checker::preview` is now `validate_watch` + `fetch_for_preview` + `preview_page`, and the editor calls the last two itself: it keeps the `FetchedPage` (status, content type and the body behind an `Arc`, so keeping and processing it copies nothing) and processes it again with whatever the form says. `preview` composes the same three, so the CLI is unchanged. `validate_watch` builds the conditions and the pipeline without fetching, to refuse a bad form before any request; `PreviewError` carries the number of the step a problem came from (`PipelineError::step`), so the form can point at the step row. The step is read from the error value, not parsed out of the message.

The processing thread limit (one per key, 32 in all) is keyed by a slot that is now passed in. A check passes its watch id; the editor passes a key of its own for the form. This matters: a preview thread that is still running (the browser dropped the request, or a jq program is slow) holds its key, and if the key were the watch id the next scheduled check of that watch would be refused and recorded as a failed check, raising its failure streak and backoff. A test (`slot_tests.rs`) holds a preview's slot and checks that `check` on the same watch succeeds. The same limit is shared by the whole process, which is why tests that run side by side in one process each use a slot of their own.

## The test button

`Notifier::test_once` sends a test notification with no retries; `test` (used by `vigil notify test`) keeps the notifier's retry policy. A person is waiting behind the button in the web UI, and the default policy can take 42 seconds to give up (2, 10 and 30 second waits), longer than a browser or a proxy waits. One attempt answers at once with the channel's own error, and the person can press the button again. Either way the result is a row in the delivery log without a watch, and a test is never kept in the outbox for later tries.

## Web UI foundations

Pages are server-rendered with `askama` and made interactive with htmx; there is no JavaScript build step and no script of our own. `htmx.min.js` is the unmodified `dist/htmx.min.js` of the htmx.org 2.0.11 npm package (SHA-256 `d6fdc75f204e6bdefa99b69bf1e6d4ac69b8a364f77929f45c13476b4000f717`, 0BSD licence shipped next to it as `assets/htmx.LICENSE`). It was taken from the registry tarball after checking the published integrity hash, and a test pins the hash, so an edited copy cannot slip in. To upgrade, replace the file, the hash in the test and this paragraph together. CSS and JavaScript together are kept under 100 KB (a test checks), about half of which is htmx.

The page policy is `default-src 'self'` with no `unsafe-inline` and no `unsafe-eval`, `frame-ancestors 'none'`, `form-action 'self'` and `object-src 'none'`. So templates carry no `<style>`, `style=` attributes, inline scripts or event-handler attributes, and htmx is told (a `htmx-config` meta tag) not to inject its indicator styles, not to evaluate code and not to run script tags; the indicator rules are in `vigil.css`. Dialogs (`hx-confirm`) are not used: confirmation is an inline step rendered by the server. Pages are `Cache-Control: no-store`; assets carry an `ETag` (the SHA-256 that `rust-embed` computes) and are cached for a year when requested with `?v=<fingerprint>` (the first ten hex digits of that hash), which every link in the layout adds, and revalidated otherwise. The fingerprint, not the release version, so that a changed file always gets a new address; found when a stylesheet change was not picked up under an unchanged version.

Everything except `/healthz` is served under the path of `base_url` (`https://example.com/vigil` serves `/vigil/...`). The reverse proxy has to pass the prefix on rather than strip it; links, assets and redirects are all built with the prefix. `/healthz` stays at the root for container health checks. axum nests `/` at the prefix without the final slash, so the slash form is registered as well.

## Interface language

UI text is in `locales/en.toml` and `locales/uk.toml`, embedded with `include_str!`, parsed once at start-up and flattened to dotted keys (`nav.watches`). A text with a count has one key per plural form (`watches.count.one`, `.few`, `.many`, `.other`); English uses `one` and `other`, Ukrainian the CLDR integer rules for `one`, `few` and `many`. Placeholders are `{name}`. The language is the `vigil_lang` cookie if it names one we have, else the best entry of `Accept-Language` by quality, else English; a missing text falls back to English, and one missing there shows as its key. Tests make this hold: both files have the same keys (counts compared by base name, since Ukrainian has more forms), every plural has all the forms its language needs, placeholders agree, no text is empty, every string in `src/` or `templates/` that looks like a key of one of the namespaces exists, and no template holds visible words of its own. Messages that library crates produce (a notification URL parse error, a pipeline error, a fetch error) are shown as they are, in English: translating them would mean threading a language through crates that know nothing of the UI, and they quote user input, which is not translatable anyway. Messages the web crate makes itself (form validation, flash messages) come from the locale files.

## Signing in

One admin account, a password. `VIGIL_ADMIN_PASSWORD` set means that is the password at every start (rehashed only when it differs from the stored hash). Unset, a saved password (from an earlier start or the settings page) is kept, and when there is none a random 24-character password is made up, logged once and saved as an Argon2id hash. `--no-auth` / `no_auth` skips all of it and is announced in the log at start and in a banner on every page.

A session is a random 256-bit token in an `HttpOnly`, `SameSite=Lax` cookie (`Secure` over https, `Path` the base path), stored as its BLAKE3 hash with a 30 day sliding expiry that is written back at most once an hour. Expired sessions are removed when someone signs in. Wrong passwords are counted in memory: five in a minute lock sign-in for the rest of the minute (even for the right password, since there is only one account and an attacker is not that account), and each wrong answer is delayed by a second so that a guess costs time whether or not the limit is reached. I did not use `tower-sessions`: its sqlite store has its own migrations and sqlx version, and what we need is a table and thirty lines.

Cross-site request forgery is handled without tokens. A request that is not `GET`, `HEAD` or `OPTIONS` must carry an `Origin` that is the configured `base_url` origin or the host the request was sent to; without `Origin` the browser must say `Sec-Fetch-Site: same-origin` or `none`. A client that says neither (curl) is refused: the UI is for browsers, and the REST API in Phase 5 authenticates with a token header instead of a cookie, so it has nothing to forge. This applies with sign-in off too, where it is the only protection against a page elsewhere that posts to a server on your network.

Without sign-in there is a second hole, DNS rebinding: a page at `attacker.example` whose name is switched to your LAN address could then read and change everything as a same-origin page. So with sign-in off, requests are answered only when addressed to an IP address, `localhost`, or the `base_url` host. With a password this cannot happen: the attacker's origin has no session cookie. `/healthz` is exempt from both checks (orchestrators call it by service name). The sign-in page sends the visitor back to `next` only if it is a path on this site under the base path (never `//host`, a scheme, a backslash or a control character), and an htmx request that is refused is answered with `HX-Redirect` to the sign-in page of the page it was made from.

The base-path home address with a final slash redirects to the one without. It was first served directly, outside the session check, because routes added next to `nest` are not under its layers: a test found it. Every route of the UI is added to the router that has the layers.

## The watch list

The list is a table of rows; each row is a fragment (`GET /watch/{id}/row`) that its buttons replace in place with htmx, so the page keeps its place and scroll. Check now, pause, resume and delete are `POST`s that answer with the new row (delete answers with nothing, and first shows a confirmation row in its place: the page policy and the plan's "no browser dialogs" rule out `hx-confirm`). Without htmx they redirect to the list, so a form post still works.

Check now goes through the scheduler handle, so it obeys the global and per-host limits and joins a check that is already running. The request waits up to 60 seconds for the check to end; if it takes longer, the answer is the row with a note, and the row asks for itself again after five seconds. A paused watch can be checked by hand and stays paused. Pause, resume and delete tell the scheduler to reload at once, so they take effect now and not at the next 30 second resync.

Watches are listed by name, case-insensitively, with tags as chips; `?tag=<id>` narrows the list to a tag, and a value that is not a tag shows everything. `AppState` now carries the checker, the notifier and the scheduler handle that `vigil serve` runs, so what the UI starts is what the scheduler runs. Times are shown as "5 minutes ago" with the exact time in a tooltip; the intervals are shown as typed (`1h 30m`), in English units in every language, since that is what the form accepts.

## The watch form

Adding and editing share one form. A posted form is read into a `Draft` (every value still text, nothing checked), checked into a `Built` watch or a `Problems` set, and re-shown with what was typed if it has problems (status 422, so nothing is created). Problems are shown beside their field; a problem in a filter is shown in that filter, using the step number the pipeline reports. The web crate's own messages come from the locale files; the library's (a bad selector, a pattern that does not compile, a template error, the fetcher's complaint about an address) are shown as the library words them, in English.

Filters are a list of rows named `step-N-field`. The buttons for add, remove and move post the whole form to `/watch/steps?op=...` and get the list back, renumbered from what is typed now, so that nothing typed is lost and no JavaScript of our own is needed. Nothing is saved by them. Filters are read in the order of their numbers, not of the body, and a form without the checkboxes means they were unticked.

The settings are checked by building the watch's pipeline and conditions as a check would (`Checker::validate_watch`), so a form that passes is a watch that works. That runs on a processing thread under a slot of the form's own, named by a random `draft` id in a hidden field and hashed so that it can never be a watch's id (see "Previewing from the editor"). The scheduler refuses a second thread for a slot, so work on one slot takes turns: `SlotLocks` makes a Save that comes while a preview of the same form is still running wait for it, instead of failing with "an earlier processing is still running". A test with sixteen simultaneous saves of one form pins this. A thread that really never ends still holds its slot, and that refusal is kept.

A new watch is saved with its tags, targets and template, the scheduler is told to reload, and its first check is asked for at once (nobody waits for it), so the list soon shows a status. Saving an edit writes the check's settings only when they changed, as `vigil watch edit` does, because writing them forgets the page's `ETag` and the failure streak and moves the schedule; tags, targets and the template are applied on their own. An empty interval takes the shortest default of the chosen tags, else one hour. The forms are available in both languages; the filter hints use the same pattern syntax (`text` or `/regex/`) as the command line.

## The live preview

The form's preview panel asks `POST /watch/preview` on load and after a 700 ms pause in typing (`input` or `change` anywhere in the form, or the filter buttons, which send a `stepschanged` event because swapping fragments fires no input event). `hx-sync="this:replace"` drops a request that a newer one overtakes. The handler reads the form as it is, builds the watch with `build_for_preview` and answers with a fragment; it always answers 200 so that htmx swaps it in.

A preview needs the address, the request settings, the filters and the conditions to be right, and nothing else: a bad interval, retention, template or tag does not stop it, because they do not change what a check would store. "No kind of change ticked" is its own problem (`notify_on`), shown at the checkboxes and not blocking, because it is about notifying and not about the page. Conditions and filters are checked separately, so a mistake in one does not hide one in the other; with several filters wrong the form shows the first filter that fails.

The page is fetched once per open form and kept in `PreviewCache` (at most 8 forms, 32 MiB of bodies, 10 minutes), keyed by the form's draft id and by what the request is made of (address, timeout, user agent, headers). Editing filters re-processes the kept body; changing the address or the headers fetches again, and so does "Fetch again". The fetch goes through `Checker::fetch_for_preview`, not through the scheduler, so it does not count against the host limits: it is one request per change of the address, made on behalf of the person typing, and the cache keeps keystrokes in the filters from fetching at all. The slot's turn (see "The watch form") is held for building and for processing and not for the fetch, which can take up to the fetch timeout.

When editing, the result is compared with the watch's newest stored snapshot (the form carries the watch's id for this, which only selects what to compare with) using the same `DiffView` as the diff page, with the conditions' verdict ("would notify" or why not). A new watch, or one with no snapshot yet, says what a first check would do. Output beyond 20,000 characters is cut and counted. Nothing is ever stored by a preview.

## History and diff pages

`/watch/{id}` shows a watch's settings, its state, its last 15 checks (from `check_log`) and its last 15 notifications (from `delivery_log`, with the target's name), and has the buttons for checking, pausing and editing; since a page of its own has nothing to swap a row into, those buttons are ordinary form posts carrying a `return` field that names the page to come back to, accepted only if it is a place on this site (the same rule as the sign-in's `next`). The first check of a watch is logged as a change, because the check log has no value for it (migration 0001 predates the idea).

`/watch/{id}/history` lists the versions newest first (up to 500) with a link to each and to the difference from the version before it. `/watch/{id}/history/{snapshot}` shows one version's text (the first 100,000 characters). A version of another watch is "not found" exactly as a made-up one is, so an address cannot be used to read another watch's text by guessing ids.

`/watch/{id}/diff?from=&to=&view=` is the address that notifications link to (decided in Phase 3: `from` is the version before the change, `to` the version after). With neither given it compares the newest two; with one given, the other is the version next to it. Both layouts come from one `DiffView` (3 lines of context): inline lists the removed lines then the added ones, as a unified diff does; side by side faces each replaced line with its replacement. Words that changed inside a line are marked in both, and every added or removed line carries a sign for people who cannot tell the colours apart. Layout is chosen by `view=` and kept by the pickers; inline is the default because it works at phone width. Retention can remove a version that a notification still links to: that answers 404 with a page that says the version is gone, says how many are kept and links to the history, rather than the plain not-found page. Fewer than two versions is a page that says there is nothing to compare yet.

## The notification targets page

Targets are listed by name with their kind, their address with every secret replaced by `***` (the same `Channel::redacted` the command line uses), whether they are on, how many watches use them, and a standing warning on those whose address sends a secret over plain HTTP (the command line prints that once when you add one; a page can keep saying it). An address that no longer parses is shown as such, without repeating it.

The address is never put in a form. The edit page leaves the field empty with the hidden form as its placeholder, and an empty field keeps the stored address; a new one replaces it. Errors from the parser name what is wrong and never quote the address, and a form shown again after a mistake has an empty address field for the same reason: an address often holds a password, a token or a topic. The watch form lists targets by name and kind only.

The Send test button calls `Notifier::test_once`: one attempt, so the person who pressed it is not left waiting through the retries, with the result shown under the target (the channel's own error text, which holds no credentials) and written to the delivery log. A name that another target has is reported at the name field. Deleting asks first, in place of the row, and says how many watches stop being notified; the watches stay.

## Tags

A tag has a name, a colour, an optional default interval and default notification targets, and groups watches. The colour is one of nine names (gray, red, orange, yellow, green, teal, blue, purple, pink) that `vigil.css` has a `tag-<name>` class for; the page policy forbids `style=` attributes, so a free colour could not be shown, and a stored value outside the palette (from a hand-edited database) is shown gray and saved as gray. The names are translated; the class names are not.

The default interval applies when a watch is saved with an empty interval field: the shortest default of its tags, else an hour. It does not change a watch that has an interval, and it is not re-applied later. Default targets work at notification time: a change is sent to the watch's own enabled targets and to the enabled default targets of its tags, once each (`Store::delivery_targets`), so adding a target to a tag covers its existing watches too. The watch list links each tag chip to the list filtered by it. Deleting a tag, behind an inline confirmation, takes it off its watches and leaves them alone.

## Settings

The settings page has the language, the password, sessions and a few facts. The language is a form (`POST /settings/language`) that sets the `vigil_lang` cookie for a year, scoped to the base path and `Secure` over https, and sends the visitor back; it works with sign-in off too. Only a known code is accepted. The cookie is read before `Accept-Language`, so a person who picks a language keeps it whatever the browser says.

Changing the password asks for the current one, a new one of at least eight characters, and the new one again. A wrong current password counts against the same limiter as signing in, with the same delay, so a stolen session cannot be used to guess the password quickly. A change ends every other session (whoever knew the old password may be signed in elsewhere) and keeps the one that made it. With `VIGIL_ADMIN_PASSWORD` set the form is not offered and a post is refused, because that variable wins at every start and would silently undo the change; with sign-in off there is no password to change and no session to end. "Sign out everywhere" ends all sessions including this one. The notices after an action are chosen by a short word in the address (`?done=language`), and only the words the page knows produce a sentence, so an address cannot write text into the page. The page warns when `base_url` is not set, since notifications then carry no link.
